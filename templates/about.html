LogAI Monitor

LogAI Monitor

Version {{ version or VERSION }} · .NET 8

一套自托管的日志监控与智能分析系统。它把"设备各自发日志、出问题时没人看"这件事， 收敛成一条完整的自动化链路：采集 → 解析 → 存储 → 检索 → 过滤告警 → AI 分析 → 推送。 网络设备、服务器、容器产生的日志被统一接收与规范化，异常由规则实时捕获并推送， 存量日志则由大模型成批解读成"整体状态、问题清单与处置建议"。

面向中小规模基础设施与边缘现场：只要能发 syslog，或跑在 Docker 里，就能被纳入监控； 全部数据落在自有的 Redis（热数据）+ SQLite（冷归档） 中，界面、AI 与告警服务一体部署，不依赖外部 SaaS。

数据流一览
采集 → 解析 → 存储（Redis 热 + SQLite 冷归档）→ 检索 → 过滤告警 → AI 分析 → 推送；有事件时由实时通道立即送达页面。

功能说明

1. 日志采集

  • syslog 双协议：UDP 与 TCP 同时监听，接收网络设备、服务器、嵌入式终端通过标准 syslog 发出的日志；对端断线重连、半包与粘包均按行边界正确处理
  • 容器日志：通过 Docker 接口读取运行中容器的 stdout / stderr，无需在容器内安装任何采集代理；支持排除列表，避免把监控系统自身的日志反复采集进来
  • 外部投递：提供带令牌鉴权的日志投递接口，脚本与自动化任务可安全地把日志送进来

2. 协议解析与规范化

  • RFC 3164 与 RFC 5424 两种格式，自动识别 PRI 优先级并换算为 facility 与 severity
  • 抽出主机名、程序名、消息体等字段；对"发送方省略主机名"的常见畸形格式做了保护，不会把程序名误当成主机名
  • 编码三级回退：UTF-8 → GB18030 → Latin-1，中文日志不再乱码，非法字节以替换方式保留而不是丢弃整条
  • 规范化后的记录带统一字段（来源 / 主机 / 级别 / 程序 / 时间戳 / 消息），使后续检索、过滤与 AI 分析口径一致

3. 存储与检索

  • 数据存放于 Redis + SQLite：日志时间线 + 多维索引（来源 / 主机 / 级别）在 Redis，另有一条"待 AI 分析"队列；冷热分层把超过热窗口（默认 7 天）的日志/分析/告警哈希归档到 SQLite，Redis 只留索引，读取时自动回填
  • 保留期可配置（默认 30 天），过期日志由清理任务自动回收，索引同步维护，不会留下空壳
  • 组合检索：时间范围 × 来源 × 主机 × 级别 × 关键字，分页由存储层原生完成，日志量大时翻页依然迅速
  • 日志列表、仪表盘、告警页共用同一份数据，看到的口径始终一致

4. 实时观察

  • 实时推送：新日志、新告警、分析完成、统计变化会即时推送到已打开的页面，无需手动刷新
  • 仪表盘：日志总量与速率、级别分布、来源与主机排行、未分析积压、AI 后端与模型状态、最近告警
  • 连接客户端视图：谁在发日志、各发多少、最后活跃时间、最近一分钟速率、是否中断；按活跃度自动区分"活跃 / 空闲 / 停滞"
  • 异常可见：客户端若出现错误级别日志或长时间静默，会在列表中标出原因

5. 过滤与告警

  • 四条件组合（全部满足才命中）：级别、来源、消息关键字、正则表达式；过滤器可在页面上增删改，即时生效
  • 命中即写入告警记录（来源、主机、级别、消息、命中的规则、时间、确认状态等），可在告警页筛选、单条确认 / 全部确认 / 清除已确认
  • 级别门限：可按规则设定"只推送达到某级别以上"的告警；也支持单条规则设为"任意级别"，用于必须全部知悉的场景
  • 冷却机制：同一主机 + 同一规则在冷却期内只提醒一次，避免设备刷屏时把人淹没
  • 每条规则可独立决定是否推送 Telegram

6. AI 智能分析

  • 批量分析：调度器定期把未分析的日志成批交给大模型，输出整体状态、问题清单、严重问题计数、处置建议、受影响主机，并生成一句话告警摘要
  • 单条分析：对任意一条日志即时解读
  • 对话问答：就日志内容直接提问，模型结合上下文回答
  • 兼容多种后端：OpenAI 兼容接口（vLLM / SGLang / Ollama 的 /v1）与 Ollama 原生协议，可在设置页切换，模型列表随所选协议加载
  • 结果稳健性：对模型返回做 JSON 提取、截断修复与纠正性重试；确认失败的批次不会污染历史，也不会被无限重试
  • 分析历史：可按时间与关键字检索、查看完整结果、对历史批次重新分析

7. 通知推送

  • Telegram 告警：命中规则并同时通过级别门限与冷却检查后推送；冷却按「主机 × 规则」独立计时，避免同一问题反复刷屏
  • 凭据来源：可在设置页填写，也可由环境变量提供；设置页优先（改完即时生效）
  • 不拖累主链路：推送失败只记录日志，不影响采集与告警落库；通道未配置时告警仍会正常入库

8. 用户、权限与接口

  • 三级权限：管理员（含用户管理）、操作员（可改过滤器与设置）、只读（仅查看）
  • 认证：口令以强哈希存储，支持在线改密；会话经签名保护，登录后按角色显示可用功能
  • REST 接口：查询与写入成对提供，便于接入外部系统；写入接口需登录，日志投递接口用独立令牌

9. 运维与可靠性

  • 定时任务：AI 分析、过期清理、健康巡检、容器日志轮询，各自独立，单个任务异常不影响其它任务，失败原因可在日志中看到
  • 健康巡检与告警：定时体检三类问题——未分析积压超过阈值、AI 后端不可达、自动分析疑似停止；命中即推送，每个条件各自冷却（不会因为刚发过积压告警就吞掉 AI 宕机告警），问题恢复后再补一条恢复通知，并可每日汇总一次体检结果
  • 资源上限与自保：分页条数、单批分析量、容器日志行数、请求体大小都有硬上限，避免单个请求把内存吃满；越界的取值被收敛到上限而不是让进程崩溃
  • 可观测：每个后台任务都留正向判据——分析成功写 [Analysis] analyzed N log(s)、清理写 [Cleanup] removed …、告警推送写 [Telegram] alert sent；分析失败除日志外还在存储里留一条带原因的记录，便于事后追溯
  • 单一容器部署：应用与界面一体，仅依赖一个 Redis；配置经环境变量注入
  • 写入护栏：连接到生产库时默认禁止后台写入组件启动，避免误操作污染数据；确认接管时显式放行

10. 界面

  • 11 个主页面 + 登录页：仪表盘、日志、分析、分析历史、告警、过滤器、连接客户端、Docker 容器、设置、用户、关于；另有登录页与 404 页
  • 统一的深色侧栏与顶栏、卡片式分区、表格与级别徽标；日志详情、分析详情以弹窗呈现，不打断当前浏览位置

开发技术 Technology Stack

这个项目用以下技术开发：

语言与框架

  • C# / .NET 8 —— 后端服务、REST 接口与页面渲染，使用 ASP.NET Core minimal API
  • 模板渲染 —— 自实现的模板引擎，服务端渲染 HTML（extends / block / if / for），页面不依赖前端框架
  • 前端 —— 原生 JavaScript + CSS（无打包构建步骤），图标使用 Font Awesome

数据存储

  • Redis 7 —— 主数据存储；.NET 客户端库为 StackExchange.Redis
  • SQLite（Microsoft.Data.Sqlite）—— 冷热分层的冷存储：超过热窗口的日志/分析/告警哈希归档到磁盘，Redis 只保留 ZSET 索引
  • 数据结构选型：有序集合承载时间线与多维索引（分数=写入时间，便于范围检索与排序），哈希承载日志 / 告警 / 用户 / 客户端档案，集合承载各类注册表，日志按保留期设置 TTL

采集与外部集成

  • syslog UDP/TCP —— 基于 .NET Socket 自行实现接收循环，内置 RFC 3164 / RFC 5424 解析与编码回退
  • 容器日志 —— 直接调用 Docker Engine API（只读挂载 unix socket，不引入 Docker SDK）
  • AI 后端 —— OpenAI 兼容 REST（vLLM / SGLang / Ollama 的 /v1）与 Ollama 原生协议，由 HttpClient 调用
  • 通知 —— Telegram Bot HTTP API
  • 实时推送 —— 自实现 Engine.IO v4 长轮询（含会话鉴权与多包帧封装）

安全

  • 口令 —— scrypt 强哈希，校验参数从存储值自身读取
  • 会话 —— HMAC 签名 Cookie；写类接口要求已登录，日志投递使用独立令牌

部署与依赖

  • Docker 多阶段构建 —— SDK 镜像编译，产物拷贝到 ASP.NET Core 运行时镜像
  • 对外端口 5059（HTTP）、514/UDP 与 515/TCP（syslog）；容器时区 Asia/Shanghai
  • 第三方依赖仅 4 个 NuGet 包：StackExchange.Redis、Microsoft.Data.Sqlite、System.Text.Encoding.CodePages、scrypt 实现；其余（模板引擎、Engine.IO、调度器、协议解析）均为自实现

实现设计说明

数据模型

  • 时间线用有序集合承载，分数取写入时间，因此"某时间段内最新的 N 条"由存储层直接定位，翻页不随数据量退化
  • 多维索引（来源 / 主机 / 级别）同样以写入时间为分数，级别与时间范围可以天然叠加；三张索引与时间线在同一批写入中同步维护
  • 待分析队列独立成一条队列，AI 分析按批取走，与展示用的时间线互不干扰
  • 保留期落在每条日志上，到期由清理任务回收，并同步移除索引中的成员，不残留空索引
  • 冷热分层：热窗口内日志/分析/告警哈希在 Redis，超过后归档到 SQLite（幂等、按分数水位推进）；Redis 保留时间线/维度 ZSET，因此聚合与翻页不退化，真正读取老记录时才走 SQLite 主键回填
  • 值编码约定：文本原样存储（便于外部直接读取与正则匹配），布尔与结构化数据以 JSON 文本存储——这一约定决定了写入与读取两侧的对称实现
  • 客户端档案：每个发送方保留一份汇总记录（首见/末见、主机名、消息与错误计数、最近错误）另配两个附属结构——协议集合与最近一分钟的滑动窗口，因此"当前速率"与"是否停滞"都能即时算出，无需扫描历史

写入路径

  • 单条日志的落库是一次管道往返：哈希本体 + 时间线 + 待分析队列 + 三张索引 + 客户端档案一并提交，避免逐键往返把接收线程拖住
  • 接收与存储解耦：接收循环只负责收包与解析，落库交由存储层；落库变慢不会导致丢包，但队列有界，溢出计数（dropped）会被记录下来而不是静默丢弃
  • 接收器对外暴露收发与丢弃计数，便于判断"是没收到"还是"收到了但没落库"——这是排查采集问题最常用的两个数字

实时通道

  • 采用长轮询：客户端一次请求挂起等待，有事件立即返回，无事件则超时后重连；连接建立时校验会话，未登录的连接会被明确拒绝
  • 事件模型固定为四类：新日志、新告警、分析完成、统计变化；统计推送做了节流（每 2 秒最多一次），否则高日志量下会变成推送给客户端的主要负担
  • 推送是尽力而为的旁路：统计生成失败或推送失败只记录日志，绝不影响采集与告警落库
  • 运维动作（确认告警、删除日志、改设置）同样触发统计推送，使多个已打开页面的状态保持一致

告警判定

  • 规则条件是合取且短路求值：级别、来源、关键字、正则依次判断，前面的条件不满足就不做后面的开销（正则是其中最贵的）
  • 正则预编译并复用；规则里的正则若非法，该条规则视为不匹配而不抛异常——一条写错的正则不应该让整条采集链路中断
  • 冷却采用"仅当键不存在时写入并设过期"的原子操作，因此并发下同一主机同一规则也只会推送一次，不依赖额外的锁
  • 落库与推送分离：告警先落库（保证可追溯），推送结果不影响告警记录；单条规则可独立关闭推送，或设为"任意级别"以旁路级别门限

AI 分析

  • 批次大小有界，避免一次把过多日志塞进上下文；提示词明确要求模型输出固定键集的结构化结果，界面对这些键有确定的呈现方式
  • 模型返回要经过提取与修复：从可能夹带说明文字的输出中取出 JSON，修复被截断或括号不配对的片段；仍不合法时做一次纠正性重试
  • 两次都失败即判定该批次失败——不伪造"成功但内容为空"的结果，否则界面与统计都会失真
  • 反复失败的批次会被退役，防止一条无法解析的日志让队列永久卡在同一批
  • 历史记录的字段集按来源区分（批量与单条所需信息不同），并设置保留期，长期运行不会无限增长

调度

  • 分析、清理、健康巡检、容器轮询四类任务彼此独立：单个任务抛异常只记录该任务的失败原因与调用栈，不影响其它任务继续运行
  • 任务间隔不缓存：每次调度重新读取设置，因此改完间隔无需重启即生效
  • 同一任务不重入：上一次未结束时本轮跳过，避免慢任务堆积
  • 巡检告警的冷却状态保存在进程内，因此重启会重置冷却；对体检类告警而言这是有意的取舍——宁可重启后多提醒一次，也不要静默漏报

安全与防护

  • 写入护栏：连接到生产库时，后台写入组件默认拒绝启动并明确提示，避免"只想读一下"却改了数据；接管时需显式放行
  • 口令以强哈希存储，校验参数从存储值自身读取，因此参数的调整不会让既有口令失效
  • 会话 cookie 由服务端签名保护，客户端无法伪造；写类接口一律要求已登录，日志投递走独立令牌而非会话
  • 容器日志采集仅以只读方式访问 Docker 接口，并支持排除列表，避免采集监控系统自身而形成回环

测试与验证设计

  • 21 套自测覆盖解析、过滤、告警、会话、通知模板、提示词、调度、清理、健康巡检、客户端跟踪、Docker 采集等模块，可用命令行单独运行
  • 自测的退出码就是结论：成功 0、有断言失败 1、拒绝在 0 号库上执行写类用例 2。因此可直接串进脚本或 CI；模型等外部依赖不可用时，自测会报告失败而不是崩溃，以免把"环境没配好"误判成"功能坏了"
  • 断言刻意带上类型与量纲：例如"索引类型必须是有序集合""分数必须落在纪元秒的合理区间"。这类断言能抓住"看起来对、实际语义错"的问题——纯值比较往往抓不住
  • 夹具使用与生产一致的真实键名与类型，避免"夹具和实现一起错、测试却通过"
  • 验证分层：单元级（解析与判定）、端到端级（采集 → 落库 → 索引 → 过滤 → 告警 → 通知）、真实数据级（对线上真实日志逐字段核对）
  • 改动公共路径后执行面状回归：例如序列化或多处共用的构造函数被修改时，重新核对所有受影响接口的输出，而不是只测触发改动的那一个点
  • 破坏性操作只在隔离库上验证，并在实现中保留"生产库只读"的默认姿态
